# 任务归档

Super Productivity 中的任务归档将**已完成任务**从活动任务列表移入单独的**归档**存储。目标是保持活动列表小而快、减少设备间同步的数据量，并通过同步**要归档什么**（操作）而非完整归档内容，确保每台设备最终拥有相同的归档。归档分为两层——**近期**与**旧有**——因此近期数据更常同步，而较旧数据保留但很少传输。了解为何存在归档、两层如何工作、归档如何与时间追踪和同步交互，以及你可以恢复已归档任务，有助于理解「结束一天」、报告与同步行为。

关于时间如何记录以及存储在何处（包括归档），请参阅 [[4.14-How-Time-Is-Logged]]。关于任务归档时属性如何变化，请参阅 [[4.09-Task-Attributes]]。关于从备份文件恢复数据（与从归档恢复单个任务不同），请参阅 [[2.02-Restore-Data-From-Backup]]。

## 为何归档而不是让所有已完成任务保持活动？

若每个已完成任务都留在活动列表中，该列表会无限增长。应用将不得不加载并同步数千个任务，这会：

- **拖慢界面** — 活动列表是你每天看到并交互的内容；保持其小巧使应用保持响应。
- **增加同步体积** — 同步会随时间发送越来越多数据；归档让应用只同步**操作**（例如「归档这些任务」「将近期移到旧有」），使每台设备以相同方式更新自己的归档，而无需传输完整归档。

因此已完成任务被**移出**活动列表进入**归档存储**（在磁盘上，而非主内存列表中）。它们仍是你数据的一部分，用于**报告与历史**，但不再出现在项目列表、Today 视图或 Schedule 中。应用将它们视为**同一任务**（相同 ID）；只是处于不同的**存储层**。

## 两层：近期归档与旧有归档

归档分为两层，以平衡**近期数据的访问**与**同步体积**：

- **近期归档（young）** — 保存**最近**归档的任务（例如过去 21 天内）。该层包含在**每日或频繁同步**中，因此设备对「刚归档」的数据保持同步。这些任务的时间追踪数据也在此。
- **旧有归档（old）** — 保存**较旧**的已归档任务（例如超过 21 天）。该层仅在应用将数据从近期归档**刷入（flush）**旧有归档时更新（例如每隔几周）。同步随后携带该刷入操作，使所有设备将相同任务从近期移到旧有。旧有归档**很少**完整传输；它随每次刷入在各设备上增长。

**为何是 21 天？** — 阈值（例如自完成后 21 天）是一种平衡：足够长，使「近期」覆盖正常复盘与报告需求；足够短，使近期层不会永远增长。若不定期将近期 **flush** → 旧有，近期归档会无限增长，同步也会变重。刷入使近期层保持有界。

**概念角色：**

- **近期归档** — 「刚归档」的任务及其时间数据；经常同步；便于需要最近几周数据的报告快速访问。
- **旧有归档** — 长期历史；仅在刷入时更新；相同数据，同步更少。

## 生命周期：从活动到已归档（再回来）

1. **活动** — 你创建并处理任务；它们位于**活动任务列表**（你在项目、Today、Schedule 中看到的）。
2. **已完成** — 你将任务标为完成。它留在活动列表中，直到应用（或你通过「结束一天」等）**归档**它。
3. **已归档（近期）** — 任务被归档时，它们（及其**时间追踪数据**）写入**近期**归档。它们从活动列表中移除。同一任务 ID 现在指向归档中的一行。归档是**不可变的**：你不就地编辑已归档任务；若需要回来，你**恢复**它。
4. **刷入（近期 → 旧有）** — 定期地，应用将超过阈值的任务（及时间数据）从近期归档**刷入**旧有归档。刷入后，近期归档不再持有该数据；旧有归档持有。近期层中的时间追踪移到旧有层，近期时间追踪存储被清空，以免无限增长。
5. **恢复** — 你可以**恢复**已归档任务：应用将其从归档移回**活动**列表。这是已归档任务再次变为活动的唯一方式。重复的「归档」操作是安全的：若任务已归档，应用会跳过，因此同步重试或重复不会造成不一致状态。

**不变量：** 子任务与其父任务**一起**归档（并刷入），以保留层级。任务 ID 以确定性顺序存储，以便同步在每台设备上重放相同操作时，每台设备最终有相同的归档布局。

## 同步如何在不发送归档的情况下工作

应用**不同步完整归档**作为一个大文件。相反，它同步**操作**，例如「归档这些任务」与「将近期刷入旧有」。每台设备：

- 接收相同操作（通过操作日志或同步协议）。
- 本地运行**相同的确定性逻辑**：例如将这些任务从活动 → 近期归档，或将数据从近期 → 旧有。
- 将结果写入其**本地**归档存储。

因为逻辑是确定性的，**所有设备最终拥有相同的归档内容**，而无需通过网络发送归档数据。这使同步载荷保持较小，并避免传输数年的已完成任务。若操作失败（例如刷入），应用可回滚到先前状态，使归档保持一致。

## 归档后的时间追踪与报告

当任务被归档时，其**时间追踪数据**随之一起移入近期归档。当应用刷入近期 → 旧有时，近期层中的**所有**时间追踪都移到旧有层（并清空近期时间追踪存储）。因此：

- **时间数据不会丢失** — 它存在于归档中（近期或旧有），并仍与任务关联。
- **报告与历史** — 当你运行报告或按项目/标签/日期查看时间时，应用从三处**合并**时间数据：**活动**列表（当前工作）、**近期**归档与**旧有**归档。合并时优先级通常为：当前 > 近期 > 旧有，因此你看到单一一致视图。报告期望包含已归档任务的时间；可见性由日期范围以及哪一层持有数据决定。

因此归档为报告**保留**时间数据；只是将其移入归档存储，使活动列表与频繁同步保持轻量。

## 你可以依赖什么

- **已归档任务不可变** — 你不在归档中编辑它们；需要时先恢复再编辑。
- **恢复是回到活动的唯一方式** — 已归档任务仅通过显式恢复再次变为活动。
- **操作可安全重试** — 当工作已完成时，重复的归档或刷入操作会被忽略，因此同步与重试不会损坏归档。
- **同一任务，不同层** — 任务是同一逻辑实体（相同 ID）；只有其存储层（活动 vs 近期归档 vs 旧有归档）变化。

## 心智模型

想象**两个仓库**：一个小的**活动**仓库（你每天看到的列表）和一个更大的**归档**仓库，有两个架子——**近期**架（最近约 21 天，经常同步）与**深层**架（较旧，仅在应用刷入时更新）。当你完成任务时，应用将它们（及其时间数据）移到近期架。定期地将旧项目从近期架移到深层架。要同步时，应用不运送仓库；它运送**移动指令**。每台设备运行相同指令并最终得到相同布局。若你需要任务回到活动列表，你从归档**恢复**它。

## 小结

- **目的** — 保持活动列表小而快；保持同步小；通过同步操作而非归档数据，保持所有设备的归档一致。
- **两层** — 近期归档（约 21 天），经常同步；旧有归档（较旧数据），在刷入时更新。刷入防止近期层永远增长。
- **生命周期** — 活动 → 已完成 → 已归档（近期，含时间）→ 刷入到旧有；**恢复**将任务返回活动。
- **时间追踪** — 随任务移到归档；报告合并活动 + 近期 + 旧有，使历史时间仍可用。
- **同步** — 同步操作（归档、刷入）；每台设备本地应用它们，使归档匹配而无需传输完整归档内容。
